# sqlsh Architecture

`sqlsh` is a minimal interactive SQLite shell whose distinguishing feature is
zsh-style completion: pressing `<Tab>` opens a navigable menu of candidates
derived from the live database schema and, where useful, its contents.

This document records how the program is decomposed and why each structural
decision was taken. It is the reference for behaviour; when the code and this
document disagree, one of them is a bug.

Project state — goals, roadmap, phase status, the gate and the waived
diagnostics — lives in `PROJECT.md`, which is the single source of truth.
This document holds design detail only.

## Scope and non-goals

`sqlsh` is a drop-in replacement for `sqlite3(1)`: the same dot commands, the
same output modes and the same command-line flags, with completion, colour and
theming added. Upstream defaults are available exactly, behind `--compat`.

Non-goals, stated so they are not accidentally pursued:

- **Bundled SQLite extensions** (`sqlar`, `zipfile`, `sha3`, `sqlite3expert`,
  `sqlite3recover`, `sqlite3_intck`, `sqlite3session`, `dbdata`). These are the
  bulk of upstream `shell.c`. The 21 dot commands that need them are
  recognised and refused with a message naming the extension, so the gap is
  documented rather than discovered. See `PROJECT.md` Phase 6.
- A complete SQL parser. Completion needs to know *where the cursor is*, not
  what the query means.
- Windows support. POSIX termios is assumed throughout.

## Relationship to upstream sqlite3

The upstream client is `shell.c`: 37,373 lines in the pinned 3.53.3, over a
megabyte, machine-generated by concatenating `src/shell.c.in` with a dozen
extension sources. It cannot be meaningfully diffed, re-derived, or
hand-maintained, and patching a completion engine into it would mean owning a
blob nobody in this repository wrote.

`sqlsh` is therefore a clean-room reimplementation against the public `sqlite3`
C API rather than a textual fork. Upstream `shell.c` is kept for consultation
only, copied on demand into `reference/` by `make reference` — out of the same
amalgamation the flake already pins, so the project names one sqlite version,
not two — and excluded from git. When we want to match an upstream behaviour
exactly — quoting rules, a dot command's flag set, the precise column-width
algorithm — we read it there and reimplement deliberately.

The tradeoff accepted: parity must be built and verified deliberately rather
than inherited. It is therefore measured, not claimed — from Phase 5 the gate
runs a differential suite that executes the same input through `sqlsh --compat`
and through the `sqlite3` binary from the flake and compares byte for byte. The
gain: every line in `src/` is ours, small, and auditable.

## Dependencies

One: `libsqlite3`. Nothing else beyond libc and POSIX.

Notably absent is any line-editing library. This is not asceticism — it is
forced. GNU readline, libedit, and linenoise all implement completion as
*print a list of candidates and return to the prompt*. None has a concept of a
persistent, navigable selection menu that narrows as you keep typing. Getting
zsh behaviour means owning the terminal, so we own it (`line.c`, `menu.c`).

Two build paths exist for SQLite itself:

- `make` links the system `libsqlite3` found by `pkg-config`. The flake pins
  nixpkgs, so this is reproducible.
- `make SQLITE=vendored` compiles the SQLite amalgamation instead, producing a
  binary with no external SQLite dependency. The amalgamation is fetched by the
  flake (`SQLITE_AMALGAMATION`), never committed — it is 9.4 MB and 266k lines.

Objects are written to `build/<backend>/<mode>/`. Keying the directory by both
is not incidental: a single shared `build/` lets `make test` link objects that
an earlier `make debug` compiled without sanitizers, so the test suite runs
uninstrumented while appearing to pass. The devShell also warns when the pinned
amalgamation and the system `libsqlite3` disagree on version.

Both paths must keep working, and the amalgamation version in `flake.nix` is
pinned to match `pkgs.sqlite` so the two agree. Bump them together.

## Module decomposition

Each module is a `.c` in `src/` with a header in `include/`, owns one concern,
and depends only on those below it. No module reaches into another's internals.

```
main.c      argument parsing (upstream flag set) and nothing else
  |
  +-- shell.c   the session: the current connection and the auxiliary ones,
  |     |       the .output/.once redirect, the switches, statement
  |     |       execution, the REPL, the init files
  |     |
  |     +-- dot.c     the command table and dispatch: 76 rows,
  |     |             64 implemented and 12 refused
  |     +-- schema.c  .schema .fullschema .dump .databases .indexes .tables
  |     |             .dbinfo .dbtotxt .clone .lint -- byte-exact ports
  |     +-- import.c  .import (RFC 4180 CSV and ASCII-delimited), .excel/.www
  |     |
  |     +-- out.c    the 22 output-mode presets, box drawing, type-aware colour
  |           |
  |           +-- width.c   UTF-8 display width, also used by menu.c
  |
  +-- line.c    raw-mode line editor: keys, cursor, history, redraw
  |     |
  |     +-- hl.c      syntax highlighting of the buffer being typed
  |     +-- menu.c    completion menu: layout, navigation, rendering
  |           |
  |           +-- comp.c    candidate generation: asks sqlctx where we are,
  |                 |       asks db what exists, returns a candidate list
  |                 +-- sqlctx.c   SQL tokenizer + cursor-context state machine
  |
  +-- theme.c   colour table, terminal capability detection, theme file
  +-- db.c      sqlite3 handle, statement execution, schema introspection,
                the value cache
```

`out.c` sits under `db.c` in the include order, not above it: `db.c` hands it
typed values and column names and decides nothing about appearance, and nothing
above `db.c` includes `<sqlite3.h>`. That split is what lets the formatter be
tested on synthetic rows, and what lets the differential parity suite treat the
whole pipeline as one function from query to bytes.

`db.c` applies upstream's connection settings itself, on the first open and on
every `.open`: double-quoted string literals off (DDL and DML), defensive on,
trusted-schema off, statement scan-status off, extension loading enabled. They
are behaviour, not decoration — with DQS off, `SELECT "typo"` is an error
rather than a string. DQS in particular has to be set explicitly because
upstream compiles its own SQLite with `-DSQLITE_DQS=0`, while sqlsh links a
shared `libsqlite3` that may have been built either way; setting it here makes
the two behave identically whichever library is underneath.

A dot command is handed a `Shell` and reaches everything through it, so the
program has no globals below `main.c`: the redirect a command writes to is
`shell_out(sh)`, which is the `.output` file while one is active and the base
stream otherwise. That is also why `.once` works without the REPL knowing about
it — the shell ends the redirect after the next statement.

`sqlctx.c` and `comp.c` are pure with respect to the terminal: they take a
buffer and a cursor offset and return data. That is what makes the completion
engine unit-testable without a pty, and it is the main reason the decomposition
looks the way it does.

## The completion pipeline

A `<Tab>` at cursor offset *n* in buffer *b* flows:

1. **`sqlctx_analyze(b, n)`** tokenizes *b* — respecting string literals,
   `--`/`/* */` comments, and quoted identifiers (`"x"`, `` `x` ``, `[x]`) —
   then walks the token stream to produce a `SqlContext`:

   ```c
   typedef struct {
       SqlCtxKind kind;       /* what may appear here */
       const char *prefix;    /* the partial word under the cursor */
       size_t      prefix_len;
       TableRef    tables[SQLCTX_MAX_TABLES];  /* from FROM/JOIN, with aliases */
       size_t      table_count;
       char        column[SQLCTX_MAX_IDENT];   /* for VALUE contexts */
   } SqlContext;
   ```

   `kind` is one of: `CTX_DOT_COMMAND`, `CTX_DOT_ARG`, `CTX_STATEMENT_START`,
   `CTX_SELECT_LIST`, `CTX_TABLE`, `CTX_COLUMN`, `CTX_VALUE`, `CTX_KEYWORD`,
   `CTX_UNKNOWN`.

2. **`comp_candidates(ctx, db)`** maps the context to candidate sources:

   | Context              | Candidates                                        |
   |----------------------|---------------------------------------------------|
   | `CTX_DOT_COMMAND`    | the dot-command table in `dot.c`                  |
   | `CTX_DOT_ARG`        | per-command: table names, modes, filenames        |
   | `CTX_STATEMENT_START`| statement keywords (`SELECT`, `INSERT`, …)        |
   | `CTX_SELECT_LIST`    | columns of tables already in `FROM`; else all     |
   | `CTX_TABLE`          | tables and views                                  |
   | `CTX_COLUMN`         | columns scoped to the `FROM` set, alias-qualified |
   | `CTX_VALUE`          | distinct values of the column being compared      |
   | `CTX_KEYWORD`        | keywords valid after the preceding token          |

   Scoping is the point. `SELECT * FROM companies WHERE <tab>` must offer the
   seven columns of `companies`, not every column in the database.

3. **`menu_show(candidates)`** renders below the prompt and takes over input:
   `Tab`/`→`/`Ctrl-N` next, `Shift-Tab`/`←`/`Ctrl-P` previous, `Enter` accept,
   `Esc`/`Ctrl-G` dismiss. Typing narrows the list in place rather than
   dismissing it. A unique candidate is inserted without ever drawing a menu.

### Value completion

`CTX_VALUE` is the only context that reads user data, so it is bounded:

- query is `SELECT DISTINCT <col> FROM <tbl> LIMIT 200`, identifiers quoted;
- a `sqlite3_progress_handler` aborts it after ~150 ms, yielding no menu rather
  than a stall;
- results are cached per `(table, column)` for the session and invalidated when
  a statement that modifies the database is executed;
- when the cap is hit the menu says so, so a truncated list is never mistaken
  for a complete one.

This is on by default. `.complete values off` disables it for sessions against
databases where even a capped scan is unwelcome.

## Highlighting and theming

`hl_write(out, text, from, to, schema)` writes a window of the line being typed,
coloured. It reuses `sqlctx.c`'s lexer rather than carrying one of its own — two
lexers would drift, and the colour would stop agreeing with the completion — and
it analyses the whole line even when only part of it is drawn, because a string
that opened before the window still colours what follows.

`hl.c` knows nothing about a database. Schema lookups arrive as four callbacks:

```c
typedef struct {
    bool (*is_keyword)(void *ctx, const char *name, size_t len);
    bool (*is_function)(void *ctx, const char *name, size_t len);
    bool (*is_table)(void *ctx, const char *name, size_t len, bool *is_view);
    bool (*is_column)(void *ctx, const char *name, size_t len,
                      const SqlCtxTable *tables, size_t ntables);
    void *ctx;
} HlSchema;
```

`main.c` supplies them, `line.c` merely carries them — the same injection as
`LineCompleter`, and the same reason: the layering rule that nothing above
`db.c` includes `<sqlite3.h>`, and the practical one that every colouring
decision is then testable against a stub. The callbacks are asked once per
identifier per keystroke, so not one of them may query: each answers from a
cache `db.c` already keeps and invalidates on the schema cookie. Columns are
looked up only in the tables `sql_context` reports for the statement, which is
why `SELECT id` leaves `id` plain and `SELECT id FROM users` colours it.

The payoff is that a name the database does not know stays the terminal's plain
foreground, so a typo is visible before the statement is run.

Nothing in the program hardcodes a colour. `theme.c` holds one SGR string per
style, and the built-in palettes — `default`, `dark`, `light` and the
16-colour-safe `basic` — are theme-file *text* inside the binary, parsed by the
same parser a user's file goes through. There is nothing to install, and a
shipped theme cannot use anything a user's theme may not.

A theme file is INI: `[menu]`, `[syntax]` and `[output]` sections over
`key = value` lines, where a value is attributes plus at most one foreground and
one background colour (`bold blue`, `dim`, `underline #ff0080 on 52`, `none`).
A line whose first non-blank character is `#` is a comment; `--` comments to end
of line, as in SQL — `#` cannot, because a value is the one place a `#rrggbb`
colour appears. Unknown sections, keys and values are reported and skipped: a
typo costs the user that one line, never the palette and never the shell.

`theme_dump` writes the live palette back out in that format, so `.theme` is a
listing and a starting point for editing at once; a test asserts the round trip
for every shipped palette. `.theme` also takes `list`, `reload`, `on`/`off`, or
a built-in name or file path. The theme file lives at
`$XDG_CONFIG_HOME/sqlsh/theme`, defaulting to `~/.config/sqlsh/theme`, and
`-noinit` suppresses it exactly as it suppresses `~/.sqliterc`.

## Terminal handling

`line.c` puts the terminal in raw mode with `tcsetattr`, restoring it from an
`atexit` handler and from `SIGINT`/`SIGTERM`/`SIGQUIT`/`SIGHUP` handlers — a
shell that leaves a terminal in raw mode after a crash is worse than no shell.
`SIGWINCH` triggers a re-layout of any open menu.

Output uses plain ANSI escapes; no terminfo, no ncurses. The set used is small
and universally supported (cursor movement, erase line, erase to end of screen,
SGR). When `stdout` is not a tty, `sqlsh` reads lines with `fgets` and does no
editing at all, so pipes keep working.

Known edge cases, tracked rather than hidden: input lines longer than the
terminal width and multi-line statement continuation. UTF-8 display width is
handled by `width.c` since Phase 5.

## Error handling conventions

- Functions that can fail return `bool` or a negative `int`, never a sentinel
  pointer that the caller is expected to compare against something.
- Allocation failure is reported upward, not fatal, except in `main`.
- Every `sqlite3_stmt` is finalized on every path, including error paths.
- No global mutable state outside `main.c`'s single `Shell` struct, which is
  passed explicitly to everything that needs it.

## Testing

`tests/` uses the template's minunit. The valuable tests are the pure ones:
`sqlctx_analyze` over a table of (input, cursor, expected context) cases, and
`comp_candidates` against the fixture database. The line editor and menu are
exercised by hand and, later, by driving a pty from a script.

`tests/test.db` is generated from `tests/fixtures.sql` by `make fixtures` and is
not committed. It deliberately contains the shapes that break naive completion:
a reserved-word column name, an identifier needing quoting, a table with many
distinct values in one column and few in another, a view, and a self-referencing
foreign key.

The user's `companies.db` is a read-only symlink into their notes. It is used
for manual comparison against `sqlite3(1)` and is never written to.
